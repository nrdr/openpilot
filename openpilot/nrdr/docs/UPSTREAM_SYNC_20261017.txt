Model/runtime migration

Included: generic ONNX and separate warp compilation, native and legacy model
adapters, current CD210 default, precompiled Cinque Terre v2 Chestnut default,
per-model tinygrad compiler provenance, and paired Chestnut telemetry.
hardwared owns USB/power/link chestnutState; modeld owns chestnutGpuState.
No duplicate publisher owns the same service. Existing hardware liveness/cache
workers are preserved. Logical img/big_img camera inputs exclude recurrent
state_img_q. Legacy frame routing follows artifact layout, not Chestnut alone.

Both model runners stamp the same action horizon/frame identity before adjacent
modelV2/modelDataV2SP publications. This preserves the metadata consumed by
lane centering and firmware timing; it is not a timing recalibration.

New compiler builds use temporary outputs, reload/check their ABI, then replace
the model and provenance stamp. A failed compile leaves the prior artifact
untouched; mismatched/interrupted artifact+stamp pairs fail admission. SCons
declares both outputs, so a missing stamp forces rebuilding. C3/C4 warp build
targets are included; that does not imply live validation on both devices.
Compiler CPU affinity is inherited, not pinned to offline CPU7. Chestnut warp
link failure is a build error, not fake success. Release gates check compiler/
source hashes, QCOM backend, shared-camera warps and exact model weights without
executing pickle contents. The optional Chestnut/custom big-model path has NOT
received native GPU/hardware validation here; the C4 has no Chestnut connected.

Original drive findings are BASELINE observations

The October 17 Civic circle ran clean e1d7156b5d with opendbc 528bd887ba, not
this integration. Early turn-in analysis suggests a prediction-horizon and
model/lane-centering interaction; measured geometry is broadly close, not a
proven perfect ratio. PCM analysis shows coupled speed-servo/gas-ceiling
transitions, negative integral corrections, inverse sensitivity and some brake
handoffs, not simply every event being a zero gas command. These are supported
hypotheses from closed-loop logs, not a new controller tune or a claimed cure.

Baseline timing analysis found roughly 85.7 Hz effective controlsd delivery
while longitudinal-active versus 98.8 Hz lateral-only, with card/E4 near 99 Hz.
State fingerprints support actual held commands/fewer updates rather than just
logger loss. Core-4 contention is indicated, but the logs do not isolate every
function's contribution. Separate bounded native replay benchmarks measure
learner cost on little cores 0-2; they do not establish core-4 or onroad Hz
causality. Nothing here demonstrates that the runtime migration fixed early
turn-in, PCM comfort or scheduling. No replacement delay/gain is certified.
